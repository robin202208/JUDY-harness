# 升级记账

每次把上游 DSH 升级进 JUDY，都在这张表里加一行。**这张表是用来做决策的，不是用来写周报的**：
`耗时` 决定下次排期，`根因` / `预防动作` 决定要不要把某个补丁上移到插件层。

| 日期 | 从 | 到 | 冲突文件 | 级别 | 耗时(分) | 根因 | 预防动作 |
|---|---|---|---|---|---|---|---|
<!-- ledger:append -->

由 `scripts/upgrade.ts run` 自动追加；也可以手工补一行：

```bash
tsx scripts/upgrade.ts record \
  --from 0.1.0-rc.5 --to 0.2.0-rc.2 \
  --conflicts 7 --levels 语义+行为 --minutes 95 \
  --cause "改了 ui-sidebar/ui-conversation 的 fallback" \
  --prevention "品牌移到 slot 包，删除对上游组件的编辑"
```

生成的行长这样（示例，不是真实记录）：

```
| 2026-11-02 | 0.1.0-rc.5 | 0.2.0-rc.2 | 7 | 语义+行为 | 95 | 改了 ui-sidebar/ui-conversation 的 fallback | 品牌移到 slot 包 |
```

## 怎么填

- **冲突文件**：这次真正动手解的次数。只算"人改了文件"，不算命令执行时间。
- **级别**：按 `scripts/contracts.ts diff` 的结论填 `机械` / `语义` / `行为`；有两种就写 `语义+行为`。
  - 机械：patch 应用失败、改名冲突 —— 脚本能解。
  - 语义：契约快照 diff 命中（slot、row id、`dsh.client.inject`、env 变量增删）—— 必须人读上游文档。
  - 行为：构建过了但预检或 smoke 挂 —— 说明依赖了未文档化的内部行为，最贵。
- **耗时**：从 `git fetch` 到 `build` + `typecheck` + 预检全绿的总分钟数。
- **根因**：一句话，写"我依赖了什么不该依赖的东西"，不要写"上游又改了"。例：`ui-sidebar 的 fallback 被我改过`。
- **预防动作**：这次之后做了什么让下次更便宜。例：`把 brand 移到 slot 包，删除对 ui-sidebar 的编辑`。

## 两个从表里算出来的数

1. **升级人日** = 最近三次耗时的中位数 ÷ 60。目标 ≤ 2。
2. **补丁层占比** = `patches/*.patch` 的文件数 ÷ 该数字上限 20。每个补丁都要能回答"为什么不能上移到插件层"。

数字变差不是问题，**数字不在表里**才是问题。
